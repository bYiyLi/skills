# 开发计划内容与证据

计划回答“做哪些工作、按什么依赖做、如何验收、目前做到哪里”。需求回答产品承诺，
设计回答实现合同，使用指南回答操作方法，日志记录发生过的事。计划引用这些来源，
不复制成第二份产品设计。

## 内容覆盖

以下是语义要求，不是强制标题或字段名。按任务规模合并章节，保留能改变执行的内容：

| 内容 | 必须能回答的问题 |
| --- | --- |
| 目标与范围 | 本次完成后有什么可观察结果？哪些工作不在本次范围？ |
| 设计输入 | 哪些当前需求、设计章节或明确决定约束实施？ |
| 前置依赖 | 哪个工作依赖另一个结果或外部能力？如何确认依赖满足？ |
| 工作项与交付物 | 要实现、配置或迁移什么？各项输出由谁或哪个模块承担？ |
| 验收 | 每项交付物满足什么条件才算完成？用什么检查取得证据？ |
| 评审 | 除测试外核对哪些设计、一致性或遗漏问题？发现问题如何闭环？ |
| 完成条件 | 哪些交付物、检查和评审必须同时完成？ |
| 当前状态与证据 | 已做什么、实际检查了什么、还有哪些阻塞？ |

使用仓库已有任务/验收标识；需要跨文档追踪时再加稳定 ID。不要编造负责人、日期、
工期或百分比。若缺少外部依赖，记录所需能力和受影响工作，不推断依赖已经完成。

## 工作项、验收与设计的关系

每个工作项有明确输出和验收入口；每条验收覆盖一个已承诺交付物。允许多项工作共享
一次集成验收，但不能用只跑单元测试代替所需的实际连接、构建产物或部署环境验证。

例如开发环境阶段可以按当前技术栈覆盖：工具版本与依赖安装、仓库结构、构建与启动、
格式/静态检查、测试入口、真实底层集成、CI、开发说明。只有已确认需求使某项适用时
才纳入；不要据此强制所有项目引入容器、发布平台、监控或额外框架。

技术方案已由设计确定时，计划写关联来源和实现任务。字段命名、序列化或 adapter
mapping 能从现有合同确定时属于工程工作，不重新要求用户设计。实际存在两种会改变
调用方结果的可行语义时，说明具体输入与结果分歧，只暂停依赖该决定的工作。

## 状态与完成证据

沿用仓库状态表达。没有约定时，用普通文字区分计划中、进行中、阻塞和已完成即可，
不新增审批状态机或 frontmatter schema。

- 验收标准是应达到的结果；验收记录是实际发生的观察，两者分开。
- 证据注明检查范围、命令或观察方法、环境、结果和被验证的 commit 或工作树状态。
  未提交工作用准确的工作树描述，不虚构 commit；后续改动使证据失效时复验受影响项。
- 未运行、失败、被阻塞、跳过和通过不能混用；没有收集到预期测试不是通过。
- 评审结论必须覆盖实际检查范围；记录影响验收的发现、修复和复验。一次绿测不能证明
  没有缺陷，也不需要无理由循环相同检查。
- Phase 完成要求该范围的交付物、必需检查及影响验收的评审问题全部闭环；提交或推送
  只有在任务或仓库明确要求时才属于完成条件，并另行核对真实结果。

不要为匹配现状删除未完成任务、改弱验收或把失败项挪到未来 Phase。变更范围需要已有
授权与理由，并保留原要求和变化的可追溯关系。进度更新不等于用户接受了新产品设计。

## 总计划与历史

总计划只保存各阶段目标、依赖、状态摘要和详情链接。Phase 文档维护该阶段完整工作与
验收证据；引用日志可补充历史，但不能代替当前完成依据。仅有一个阶段时不强制额外
创建总计划。

已完成阶段可以保留计划并补充实际结果；不要把计划整体改成事后总结而丢掉原验收。
设计或实现变化影响旧结论时标明证据适用范围，不把旧成功静默用于当前版本。
