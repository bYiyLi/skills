# Software Documentation Taxonomy

仅在文档类型未知、混杂或标题与实际读者目标不一致时使用本分类。

| Observable reader goal | Document type | Owned result | Nearest boundary |
| --- | --- | --- | --- |
| 决定做什么、约束什么、如何验收 | Requirements | 可评审、可验证的需求边界 | 不拥有实现结构与技术取舍 |
| 理解系统如何组织、为何这样设计 | Design | 能指导实现和设计评审的结构与决策 | 不重新定义产品承诺 |
| 从零沿一条路径建立技能 | Tutorial | 完成一条可验证的学习路径 | 不承担完整参数查询 |
| 完成一个已知任务 | How-to | 完成任务并看到预期结果 | 不展开长篇原理 |
| 执行需要操作者权限、执行前检查点，或 rollback、recovery 或 escalation 边界的管理或运维任务 | Operator guide | 带权限、检查点和恢复路径的操作结果 | 不省略副作用边界 |
| 查询接口、命令、字段、返回或错误 | Reference | 与目标 baseline 对齐的查询面 | 不使用教学叙事组织事实 |
| 理解背景、原理或取舍 | Explanation | 对 why 的连贯解释 | 不伪装成可执行步骤 |

## 决策边界

- 用户明确指定类型且该类型与读者目标一致时，保留该类型。
- 标题与读者目标冲突时，以读者目标为准，并在修订结果中说明类型变化。
- 一个请求包含多个独立读者目标时，分别分类并默认拆成不同文档。同一读者完成同一结果
  必须连续使用这些内容，或宿主结果明确要求单文件时，可以保留一个文档；每个分区仍维持
  自己的类型和目标边界，并说明组合带来的导航限制。
- “用户手册”“开发指南”“技术文档”“FAQ”不是足以决定结构的类型；继续识别其中
  的学习、任务、查询或解释目标。
- 面向使用者的产品概念 explanation 属于使用文档范围；面向研发评审的内部结构和
  取舍属于 design。

如果读者目标仍不足以区分相邻类型，保留未决分类，并请求能改变选择的最小事实。
