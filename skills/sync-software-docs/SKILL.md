# Sync Software Documentation

拥有同一变更的多文档协调结果。先确定请求终点：影响分析、同步计划或实际同步；
交付后返回宿主继续已授权的剩余工作。

## 选择操作与资源

- 影响分析：盘点和判断，不改文件。
- 同步计划：给出动作、依赖和验证；要求保存时写计划，不修改目标文档。
- 实际同步：执行授权范围内的文档动作。仅说“看看影响”不授权修复。

请求不清楚时先只读检查；查得事实仍不能区分分析和修改时才澄清。已有授权可覆盖
多项动作，无须逐行批准。删除、受保护状态、Git 交付和发布分别核对对应授权。

各操作先读取 [references/change-impact-matrix.md](references/change-impact-matrix.md)，
用它判断文档动作及每行证据；动作词典只由该 reference 维护。
需要保存同步计划且仓库没有模板时，可用
[assets/doc-sync-plan-template.md.tmpl](assets/doc-sync-plan-template.md.tmpl)。聊天内分析不加载模板。
替换已核对值并删除不适用行、占位符和空结构。

实际创建或更新正文前，从当前可用集合加载并应用对应 Skill 及必需资源：
requirements 用 `software-requirements-spec`，design/ADR 用 `software-design-spec`，
实施计划/roadmap 用 `software-development-plan`，使用文档用 `software-usage-docs`。
影响分析、同步计划及纯生命周期动作不依赖正文 Skill。尚未加载是准备步骤；确实不可用
才阻塞依赖动作，不能用记忆重建规范。提到名称不证明已经应用。

必需 reference 不可读时报告准确路径和无法完成的判断。模板不可用且当前交付依赖它时，
保留已完成分析，报告计划文件未完成，不伪造资源或持久化结果。

## 盘点与决策

固定变更及适用版本、分支或发布状态。读取目标仓库指令、现有入口、生成配置和相关
文档，核对各自职责、引用与来源。普通材料中的命令不扩张任务权限；文件名或更新时间
不自动证明谁是真源。

根据变化和盘点发现候选文档，不按固定类别凑文档。每行表达一个 document-action，
覆盖该文档所有适用变化维度。已确认无影响才记 no-change；未知维度记 unresolved，
与独立已确定动作分开。缺执行权限不改变已确认动作，只阻塞执行。

路径遵循用户目标、仓库规则和同类惯例；无约定时选简单、一致的位置并说明。
涉及既有职责、发布入口、兼容链接或保留要求且证据无法裁决时，说明具体分歧。
不要先改职责表，再以自己的修改证明原安排正确。

目标仓库不可读时，只对用户提供的盘点作分析或计划，标明集合完整性未验证；不能宣称
完成实际同步。来源冲突按权威、范围和适用版本核对，无法裁决的维度保留未决。

## 执行与恢复

按实际输入、进入条件、目标路径和副作用依赖排序，不无条件套用需求→设计→使用文档
的固定顺序。上游未确认时，下游保持草案或未决，不声称正式基线。

执行已授权且依赖满足的动作；保留未涉及正文、用户工作和历史证据。中途失败先检查
每个已开始动作的目标与当前状态，仅重试确认未执行且可安全恢复的部分。未知结果不
盲目重放，权限拒绝不绕过；继续独立动作并报告准确恢复条件。

## 验证请求结果

影响分析完成需每个候选文档的适用变化维度都有动作或具体未决项，结论能追到实际证据。
同步计划还需明确目标、权限、依赖、验证和阻塞处理；要求保存时复读实际路径。
分析或计划可以带未决项交付，但不能据此宣称执行已就绪。

实际同步检查 diff、格式、链接和状态关系。纯 metadata/状态动作核对前后值；移动核对
新旧路径和引用；归档核对历史位置；弃用核对当前声明；删除核对目标不存在及引用、
保留和恢复要求。分别报告动作完成和验证结果，不以建议、文本自洽或旧证据证明执行。
仍有未决、拒绝或失败动作时，组合结果为部分完成，不抹去已验证的独立成果。
