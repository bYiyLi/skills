# Nexum Operations

Own the requested Nexum operating result and its required durable evidence.
Keep research, preparation, external execution, review, and scheduled maintenance
within the actual request; selecting this Skill does not activate every operation.

## Scope and authority

Use current task authorization or an applicable standing delegation whose source,
account, action scope and limits are established in the host context. This
portable file is not evidence that its reader has delegated publishing, messaging,
Feishu writes or scheduler control. Reuse a valid delegation without redundant
approval; an explicit read-only or preparation-only request narrows it.

Discussion and read-only review return findings in chat without business writes,
logs or notifications unless those are separately requested. Operating execution
may include required Feishu recording under its existing authority. Respect
host/platform action-time confirmations and denials; finish independent authorized
preparation before asking for the actual protected action. Do not switch tools
to evade restrictions, CAPTCHAs, account recovery, payment or secret boundaries.

When authority or required evidence cannot be established, stop only the dependent
action. Report what is missing, preserve completed work, and do not turn a blocked
write into a reason to abandon independent research or preparation.

## Resolve live sources

Use available authorized tools to resolve resources by stable names and current
workspace/account. If names collide, disambiguate before writing. Do not invent
IDs or reuse stale tokens. Inspect current schemas before structured writes.

Read only sources that can change this decision. The operations hub contains
content, samples, leads, experiments, experience, opportunities, tasks and logs;
resolve the applicable tables rather than loading the database. Preserve conflicts
between evidence and a Playbook as revalidation needs. Live records do not grant
permissions or override explicit user scope.

| Operation | Read |

A scheduled business run reads its applicable business reference plus the logging
reference and matching live task contract before deriving the planned run key.
Only maintenance, guarding and recovery read scheduler mechanics; an on-time
business run does not inherit a guardian patrol.
Required resources or live contracts that cannot be read block only dependent
judgments or writes; report the exact source and do not reconstruct it from memory.

## Verify and hand back

Inspect the resulting platform state after external actions, and record only what
actually happened. Research/preparation ends with the requested evidence or
content; authorized operating execution additionally completes required records,
logs and notifications. Scheduling needs evidence from the real scheduler as well
as its registry, not just matching text fields.

Before retrying interrupted work, inspect attributable platform and Feishu state.
An external action that succeeded needs only missing durable records repaired,
not another publish or message. If action outcome is unknown, investigate rather
than replay. Report completed parts, remaining evidence, blockers and recovery
conditions separately; no persistent state or recurring job exists merely because
this Skill described it.
